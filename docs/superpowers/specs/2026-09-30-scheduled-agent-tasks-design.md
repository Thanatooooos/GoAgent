# 定时智能体任务规格说明书

状态：试点设计规格。本文记录已确认的产品语义，并标出可修改的实施默认值；不表示功能已经实现。

## 1. 目标与范围

用户可以在聊天中提出未来要执行的事，也可以在定时任务管理界面创建和管理任务。系统在约定时间运行一次任务专属 prompt，由 `internal/app/runtime` 的任务运行入口决定是否读取获准资料、调用只读工具，以及生成什么结果。需要汇报时，系统在应用内的任务专用会话给用户发消息并标记未读。

任务是统一抽象。提醒、周期汇总、条件监测和 DailyBrief 都是不同规则的定时任务；运行时均经过 runtime。体育条件监测作为首批试点。试点只保证应用内消息和未读提示，不提供站外推送，也不执行外部写操作。

本规格中的“检查”若无特别说明，指模型通过 runtime 工具获取资料。**试点不设置必查来源清单，不由任务基座核验模型是否查全资料，也不声称 `no_report` 证明事件不存在。** 是否引入独立检查核验，由试点后的漏报、误报和失败数据决定。

## 2. 术语与身份

| 概念 | 含义 |
| --- | --- |
| 任务 | 用户确认的长期配置，拥有稳定 `task_id`。 |
| 配置版本 | 一次经用户确认的完整配置快照，包含 prompt、触发规则、时区、来源与工具权限、汇报规则。 |
| 计划运行 | 某个任务在一个计划触发点对应的逻辑运行，拥有稳定 `occurrence_id`。 |
| 尝试 | 计划运行因技术错误而重试时的单次 runtime 调用，拥有独立 `attempt_id` 和 runtime session。 |
| 专用会话 | 任务需要首次汇报时创建、后续汇报复用的应用内会话。 |
| 结果信号 | runtime 最终产出的 `report`、`no_report` 或 `uncertain`。它不等于 runtime 的技术状态。 |

任务、计划运行、尝试和专用会话必须分别建模。相同 `occurrence_id` 的重试只能产生一次最终发布。任务配置的修改不覆盖旧版本；旧运行仍可追溯到当时的配置版本。

## 3. 创建与修改

### 3.1 入口与意图

聊天是主要入口；另设定时任务管理界面，支持创建、查看、修改 prompt 与触发频率、暂停、恢复、查看运行记录和手动删除。任务归属用户账号，在任意普通聊天中均可管理。

聊天中只有同时明确表达**未来要发生的动作**与**触发时间或条件**，才进入任务创建流程。例如“明天下午三点提醒我交作业”“每周五整理新论文”“某服务恢复了就告诉我”。普通事实提问不能自动创建任务。条件监测缺少轮询频率时先追问；日期已明确但钟点缺失时，预览中建议当地 09:00，用户可改。

模型从用户表达生成任务专属 prompt 和结构化配置草案。确认预览至少展示任务要做什么、何时触发、时区、可访问的资料范围与工具、何时汇报、完成或暂停规则，并可展开完整 prompt。用户明确确认后，草案才成为有效任务。等价任务默认去重；用户明确要求独立的另一个任务时允许并存。

聊天中的修改请求也先生成差异预览，再由用户确认。管理界面编辑 prompt 后，服务端重新分析其隐含的触发、来源、汇报和完成语义，并展示整个配置版本的差异；用户确认后原子地启用新版本。任何配置字段不得由模型、后台推断或权限变动悄悄扩大或改写。暂停、恢复和删除必须来自明确的用户操作；管理界面按钮本身可作为对应操作的明确确认。

### 3.2 时间与时区

创建时读取浏览器的 IANA 时区，写入确认预览并保存到配置。任务以后按保存的时区运行；用户旅行或换设备不自动改变触发时间。修改时区或频率走配置版本确认。夏令时和无效本地时间的具体折算作为调度器可测试的实施默认规则，不改变上述“保存时区”的产品语义。

## 4. 任务配置与运行作用域

任务配置至少包含：`task_id`、用户、配置版本、固定 prompt、触发规则、时区、任务生命周期状态、来源/工具权限、证据与汇报规则、最近汇报和运行所需的任务私有状态，以及可选的专用会话关联。

来源规则在创建或修改时一次性确认，运行时复用，无须每次再问。可选范围包括获准的公开网页、明确的知识库 ID、官方站点或公开服务状态接口。开放网页研究可使用较宽的网页范围；条件事件默认在 prompt 中要求官方或一手证据才能宣布达成，媒体报道只作为线索，除非用户确认放宽规则。试点由服务端强制来源权限边界，不核验模型对“官方证据”的语义判断。第一版任务运行只授予只读能力；不得自动写知识库、wiki、邮件或外部系统。权限撤销即时生效，不能因为旧配置而继续访问；新增权限不能自动扩大旧任务范围。

到点执行时，runtime 收到固定的已确认 prompt、该任务的必要历史运行状态及获准来源/工具。普通聊天历史、专用会话中的闲聊和其他任务的历史均不进入定时运行上下文。专用会话中的互动可以读取当前已确认配置并提出修改草案，但不能未经确认改变下一次运行。任务运行前不由业务层预先搜集候选资料；资料获取由 runtime 和模型使用获准只读工具完成。

## 5. 调度与执行

调度器按保存的时区和触发规则生成计划运行，持久化 `occurrence_id`、计划时间、任务配置版本和状态，并以该 ID 防止重复调度与重复发布。每次尝试都调用 `RunTask`；任务基座负责调度、状态、结果解析、版本核对和发布，runtime 负责模型回合、工具调用及运行日志。

模型须返回结构化结果信号：

| 信号 | 语义 | 默认后续动作 |
| --- | --- | --- |
| `report` | 有值得汇报的内容，带正文和可展示的来源信息。 | 通过发布门槛后写入专用会话。 |
| `no_report` | 模型认为本次没有值得汇报的内容。 | 仅保存运行记录。 |
| `uncertain` | 模型认为资料不足，无法作出判断。 | 保存原因，计入连续不确定/失败；等下次计划时间运行。 |

结果至少携带信号、报告正文或不确定原因、模型给出的来源引用，以及任务与计划运行标识。`report` 必须有可发布正文，`uncertain` 必须有原因；`no_report` 仅说明模型作出的本次判断。日报等结构化视图可在结果中附带受其页面契约约束的 artifact。解析器只验证结构和必要字段，不把来源引用存在视为资料覆盖证明。

模型调用失败、超时、预算耗尽、格式无效以及运行或发布所需持久化失败属于**技术失败**，与模型给出的 `uncertain` 区分。试点只验证结果信号格式、任务权限、当前状态、配置版本、同一计划运行的去重和发布有效期；不逐项核验工具是否覆盖来源，也不把工具调用成功解释成“检查完成”。工具返回错误后模型仍可能给出 `no_report`，这是试点要通过复盘观察的风险，不能在界面上标记为“已查全”。

技术失败允许在本次计划运行仍有效时有限重试；重试沿用同一 `occurrence_id`，每次尝试有独立日志。超过有效期则记录失败，不补发过时的一次性提醒。一次性提醒因调度故障已过期时同样跳过，在管理界面显示错过。具体重试次数、间隔及有效期采用可修改的实施默认值，并在实现与验收用例中固定；它们不改变任务计划触发时间。

发布前再次核对任务是否仍启用、配置版本是否仍为运行使用的版本、专用会话是否仍有效，以及同一计划运行是否已经发布。配置修改后的旧版本结论不发送；旧结论仍可留在运行记录供追溯。新版本按已确认的新触发规则重新运行和判断，不能沿用旧版本结论。专用会话创建、消息、未读提示和运行发布状态必须作为一个可恢复的发布动作结算；运行结束与发布之间崩溃时，恢复过程凭 `occurrence_id` 幂等结算，不制造重复消息。

## 6. 各类任务的结果规则

### 6.1 提醒与周期汇总

一次性提醒和周期汇总在计划时间应产出 `report`。这两类任务返回 `no_report` 属于无效结果并记为失败。周期汇总按计划运行和汇报，不因运行间隔内出现重大新闻而额外发布。部分资料来源不可用时，能形成有用汇总就按时发送，并明确覆盖缺口；恢复后若补到有实质影响的遗漏，可发补充消息，否则留到下期。资料完全不足则使用 `uncertain`。

DailyBrief 是每日触发的同类任务，其现有结构化页面是同一份发布结果的视图。DailyBrief 的已确认 prompt 和输出契约仍须保证 `headline`、`topSummary`、`sections/items` 等页面所需结构；自由编辑不能绕过该输出契约。它迁移到通用任务基座时不再于 `RunTask` 前收集候选资料，现有依赖候选列表的对齐/验证逻辑需相应调整。

### 6.2 条件监测

条件监测按用户确认的频率运行，首次满足条件并成功汇报后标记完成。未提供检查频率时先追问。状态条件（如“服务恢复”）在第一次运行时可依据当前状态立即汇报；事件条件（如“宣布东亚演唱会”）从任务确认时刻建立基线，确认之前的旧公告不触发。

对曾经失败或暂停的时间段，恢复后的计划运行提示模型回看缺口。试点没有独立的来源覆盖核验，因此该回看只属尽力而为，系统不维护“上次成功检查时间”，也不宣称历史已完整补查。状态条件须在汇报前以当前状态为准；曾经短暂恢复、现在又故障，不能发“已经恢复”的当前状态通知。事件条件可汇报在缺口内发布的公告，并标明发布时间。模型无法判断时返回 `uncertain`，不立即重跑。

长时间没有实质新消息时，可按低频周期向用户反馈任务仍在运行，并询问是否调整。默认：每天运行的监测任务超过一周没有新消息后才触发此类反馈，之后至少间隔一周；每周运行的任务超过一个月后触发，之后至少间隔一个月。其他频率采用可修改的对应默认值。用户不回复不会自动暂停。低频反馈属于任务状态说明，不得伪装成满足监测条件的 `report`。

## 7. 专用会话与生命周期

任务创建时不创建空会话。首次有需要发送给用户的报告或状态反馈时才创建专用会话，后续复用，并写入应用内未读提示。`no_report` 和单次 `uncertain` 只保留运行记录；持续失败达到可修改的提醒阈值时发送状态通知，恢复时可发送恢复通知。

用户删除专用会话时，任务自动暂停，保留配置和运行记录，绝不自动删除任务。删除时正在运行的尝试可以完成并保存结果，但不得向已删除会话发布。用户恢复后，下一个计划运行对暂停区间做一次尽力回看，合并仍有效的待报结果与新发现，不逐次重放每个错过的触发点；直到需要汇报时才创建新的专用会话。用户在聊天中说“停止/不要再提醒”按暂停处理。只有任务管理界面的手动删除才删除任务；删除任务不级联删除已有专用会话与消息。已完成的任务重新启用时，如原会话仍在则沿用原会话，并以新配置版本表示新阶段。

任务状态至少区分 `active`、`paused`、`completed`；手动删除是独立的终止操作，可用删除事件或墓碑记录表达，不再参与调度。计划运行至少区分 `pending`、`running`、`reported`、`no_report`、`uncertain`、`failed`、`missed`、`superseded`。状态名称可随代码约定调整，但上述用户可感知的区别不可合并。任务和运行状态由任务基座持久化，runtime session/journal 记录单次尝试的模型和工具事实，会话/消息记录用户可见的汇报；三者通过稳定 ID 关联。

## 8. 管理界面与试点观察

任务管理界面展示任务 prompt、触发频率、保存的时区、来源/工具权限、状态、专用会话入口、最近运行及结果。修改时展示版本差异。运行详情展示模型结果、技术错误和工具调用记录；不显示未经验证的“已完成来源检查”。低频反馈、持续失败和恢复信息只通过应用内会话及未读提示呈现。

体育试点保留每次尝试的结果、模型工具调用及返回状态、配置版本、计划时间和实际时间。只在纳入试点的任务数据中离线抽样复盘 `no_report`、`uncertain` 和已发送报告，参照官方赛程或结果记录漏报、误报及技术失败。复盘不阻断运行、不改变模型结果，也不构成在线检查核验。试点指标用于决定是否需要引入必查来源、工具证据覆盖核验等后续机制；当前规格不预先要求这套机制。

## 9. 当前代码与实施边界

- `internal/app/runtime/task.go` 已有非聊天 `RunTask`、模型/工具循环和任务 journal，但目前只返回文本；需支持三态结果、每次尝试身份、任务作用域和稳定的运行记录。当前对部分 journal 写入错误的忽略会影响试点复盘的可信度，实施时需修正或明确以另一持久化记录作为可靠事实来源。
- `internal/adapter/repository/postgres/runtime/task_journal.go` 与对应迁移当前按 `(task_type, task_id)` 识别 runtime task session；通用任务应把长期任务 ID 与计划运行/尝试 ID 分开，避免多次运行混入同一 session。
- `internal/app/dailybrief/service/runtime_generator.go` 目前在 runtime 前接收候选资料，并在后续按候选对齐输出；迁移时需保留页面结构契约，同时去掉任务专属的预采集路径。
- 当前会话创建/删除链路没有任务归属与暂停联动；当前聊天投递主要依赖请求流。专用会话关联、后台消息发布、站内未读以及任务管理界面均需新增或接入。
- 现有 web/KB 工具权限应进一步落实到任务确认的来源范围和 KB ID；模型可自由决定是否调用工具，但不能突破服务端批准的范围。

## 10. 验收场景

1. “明天下午三点提醒我交作业”生成预览并经确认后创建任务；无确认不触发。只有日期无钟点时展示可编辑的 09:00 建议。
2. “宇多田光如果宣布东亚演唱会就通知我”缺少轮询频率时追问；补齐后预览来源、官方证据规则及浏览器时区。
3. 普通事实问答不创建任务；重复的等价任务默认提示现有任务，用户明确要求独立任务时允许另建。
4. 到点只按已确认版本运行固定 prompt；专用会话内未经确认的闲聊不能改变下一次任务行为；配置版本变更后旧运行结果不能发布。
5. 同一计划运行重复调度、技术重试或发布后崩溃恢复，最多生成一条对应汇报消息。
6. 条件监测返回 `no_report` 时没有消息，但运行记录可查；返回 `uncertain` 时不立刻重跑，连续发生后按阈值提示。
7. 工具失败但模型返回 `no_report` 时，试点保留两者的原始运行事实供复盘，不将它显示成“检查完成”。
8. 新事件在任务创建前已宣布时不触发；当前状态首次运行就满足时可以触发；补查发现已结束的短暂状态不得发当前状态通知。
9. 首次报告才创建专用会话；后续报告复用。删除会话暂停任务；运行中结果不发往被删会话；恢复后按需创建新会话并尽力回看暂停期。
10. 暂停不删除任务；永久删除仅来自管理界面，原专用会话和消息仍可保留。已完成任务重新启用沿用仍存在的原会话。
11. 技术失败在有效期内有限重试，过期一次性提醒标为错过且不迟发；`uncertain` 等下次计划运行。
12. 每日/每周条件监测超过相应无消息阈值后才发送低频状态反馈，重复反馈遵守最小间隔，用户不回复也不自动暂停。
13. DailyBrief 经通用任务运行入口生成，结构化页面与专用会话看到同一次发布结果；其他任务允许自由正文。
14. 体育试点中，针对“球队官方宣布比赛延期则通知我”的任务，确认前的公告不触发；确认后的官方公告可以产生 `report`。离线复盘抽到一次漏报时能关联到该次计划运行、模型结果和工具记录，而不追改当时发出的消息。

## 11. 实施时需固定的可修改默认值

以下是参数化实施项，不再阻塞试点规格：技术失败的最大尝试次数和退避间隔；每类报告的有效期及调度抖动容忍度；连续 `uncertain`/失败的状态通知阈值；除每日和每周外的低频反馈阈值；夏令时跳过/重复本地时间的折算；运行记录保留期限。实现时应给出明确默认值、可修改入口及对应验收测试，不得以未定义的常量隐含产品行为。
