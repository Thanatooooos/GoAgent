# Work 第一版技术设计

日期：2026-10-01。

状态：方案已接入实际 cmd、HTTP、shared runtime、仓储和前端，当前实施与验证见 [交付报告](../reports/2026-10-02-work-delivery-audit.md)。以下接入点表格保留设计时的问题背景，不能把它们当作仍未修复的当前代码状态。已确认语义见 [产品规格](2026-10-01-work-topics-product-design.md)。

## 1. 范围与设计原则

第一版交付创建主题、主题内多段对话及事项归属、相关上下文接续、独立可编辑成果与版本恢复、进展建议与确认、关联知识库以及主题文件/链接与对话附件。各实施阶段属于内部增量，不能将未包含资料或 AI 协作的阶段称为完整第一版。

Work 业务放在 `internal/app/work`，HTTP、仓储和装配分别沿用 `internal/adapter/http`、`internal/adapter/repository/postgres`、`internal/bootstrap` 的现有分层。会话/消息复用 RAG 对话模型，执行复用 `internal/app/runtime.Runtime.Run`。新增 Work 的领域数据、访问范围和能力装配，不新增另一套模型执行循环。

不引入多人协作、复杂任务看板、在线电子表格、自动外部写入或新的定时调度。定时任务关联安排在后续，不是第一版技术交付前提。用户已确认类似 Word 的富文本正文编辑，支持标题、列表和简单表格；共同编辑对象是 Work 内创建的文档，上传文件转换后续再做。

技术方案调整为结构化富文本正文（带 schema_version 的 JSON）作为唯一保存来源，Markdown/文本仅作为 AI 阅读与生成的投影。实际采用 Tiptap 3.31.4（MIT），依赖与 lockfile 已更新；编辑器通过结构化正文转换接入标题、列表、简单表格，不以 Markdown 源码输入替代体验。

## 3. 领域模型与存储

表名暂定，新增迁移实现，禁止修改历史迁移。ID 沿用项目的分布式字符串 ID，不引入第二套身份规范。

| 概念 | 建议存储 | 主要字段及约束 |
| --- | --- | --- |
| 主题 | `t_work_topic` | ID、user_id、名称、描述、active/archived、元数据 revision、时间；所有操作校验拥有者 |
| 事项 | `t_work_item` | ID、topic_id、名称、时间；支持未分事项，不强制状态流转或截止日期 |
| 对话关联 | `t_work_conversation` | conversation_id 唯一、topic_id、user_id、默认 item_id、接续来源对话；一个对话归属一个主题 |
| 当前进展与历史 | `t_work_state`、`t_work_state_revision` | 一个主题一个当前 revision；不可变 JSON 快照保存目标、约束、决定、问题与下一步；条目有稳定 ID、可选 item_id 和依据 |
| 成果与版本 | `t_work_artifact`、`t_work_artifact_version` | 主题、可选事项、当前版本；版本含标题、结构化富文本正文及 schema_version、作者类型、来源操作和恢复来源，版本不可变 |
| 更新建议 | `t_work_proposal` | 类型 `progress_change/artifact_create/artifact_update`、目标与基准版本、规范化变更、依据、pending/applied/ignored 状态 |
| 资料关联 | `t_work_source` | topic/user、可选 conversation_id、来源种类、KB/doc ID、处理状态/错误；资料解析状态以文档处理事实为准 |
| 私有资料容器归属 | `t_work_private_knowledge` | topic/user 与内部 KB 的唯一关联，标识其不属于全局共享库 |
| 输入和执行范围 | `t_work_turn` | client_request_id、已接纳 user_message_id、topic/item/focus、task/trace/runtime session、状态、上下文版本引用及快照 |
| 写入操作事实 | `t_work_operation` | turn/action ID、输入摘要、工具调用身份、结果及对象版本；与业务写入同事务提交 |

建议让对话的默认事项与本轮事项分别存在：新对话可继承默认事项，用户可以在后续输入中选择其他事项，本轮范围落在 turn 上。历史消息按其 turn 归属选择；不把会话永久等同于单一事项。成果/进展的主要事项归属是可选的，主题共同背景保持在主题层。

普通会话表无需复制。普通聊天列表排除 Work 对话，Work 列表只查指定主题；按 ID 的普通聊天执行入口不能绕过 Work 装配来运行 Work 对话。消息读取和反馈可复用底层服务，但 HTTP 层始终校验 user/topic/conversation 的关联。

## 4. 一次 Work 对话的正式执行路径

```text
POST /work/topics/:topicId/chat
  → 登录身份与主题/事项/对话/关注成果校验
  → 按 clientRequestId 接纳或读取同一次输入
  → 创建/关联会话，保存用户消息，固定本轮事项与目标
  → Work 输入分析，确定明确指令允许的动作；歧义则澄清
  → 保存本轮背景、确认进展、成果版本及资料范围快照
  → runtime ChatService / Runtime.Run（Work 配置与能力目录）
  → 工具执行、成果保存或生成待确认建议
  → 保存助手消息与 Work 结构化关联
  → SSE 投影，刷新时按持久化状态恢复
```

传入客户端的 topic/item/conversation/artifact ID 只是选择，不是权限。模型工具参数不得设置用户身份、主题范围或任意扩大读写对象。服务端核对所有选中对象；字段指向别的用户或主题时拒绝，而非悄悄修正。

Work 的可选执行契约由 runtime 定义小型身份/范围结构及端口，Work 适配器负责加载业务内容，避免 runtime 反向依赖 `internal/app/work`。具体结构名在实施时确定，至少覆盖 topic_id、item_id、turn_id、聚焦成果、资料范围和允许动作。

建议装配专用 Work Runtime 实例，复用同一个 Runtime 类型、模型 adapter、历史压缩和 Lifecycle，但使用 Work ContextSources、工具目录和历史适配器。普通聊天的全局记忆/画像 loader 与自动观察 hook 不挂在 Work 实例上；现有全局观察的列表扫描也排除 Work 关联，不能仅跳过当前 hook 就认为已隔离。

客户端生成 request ID；同一用户/主题/request ID 只接纳一次消息。重连读取既有流或结果，不重新执行模型。进程重启后的未完成执行标明中断并核对写入结果，不能自动重放有副作用的工具。若用户重试，保留原输入和操作事实以去重。

## 5. 上下文与历史

本轮快照记录已确认的主题共同背景、当前事项进展、明确聚焦的成果版本以及用户指定的接续对话。主题级栏目较大时，优先保留当前约束和决定，待办按事项选择；其余通过读取能力按需取得。上下文预算沿用既有 token 预算，并记录省略与实际引用的内容。

当前对话的原始消息仍保存在既有消息仓储。Work 历史适配器在同一会话含多个事项时，以本轮事项和显式接续范围选择消息，摘要也记录覆盖消息和事项范围；不能拿整个会话的旧摘要替代当前事项历史。

新增 `work_search_history` 与 `work_read_history`，查询必须带服务端 user/topic 范围，默认限定当前事项及主题共同背景；用户明确要求跨事项回顾时可在同主题内扩大。第一版建议基于持久化消息的受限文本检索和定向读取，结合可用摘要，不要求先复制全量历史到新向量库。排序能力可以渐进改进，但真实历史接续不能只覆盖模型曾主动 archive 的 episode。

未确认建议可以作为“待处理建议”读取，不能作为当前决定。历史检索的旧状态不得替代本轮已确认快照。用户要求复盘旧决定时读取当时版本，并明确当时和现在的差别。

引用结构至少支持历史消息 ID、成果版本 ID、进展 revision/条目 ID 以及知识库 chunk。由受控工具返回可引用对象，服务端校验归属后持久化，模型自由文本中的任意 ID 不直接变成有效引用。引用入口可打开对应版本或显示来源已不可用。

## 6. AI 成果写入与进展确认

建议能力目录：读取进展/成果、搜索/读取范围内历史、受限资料检索、创建或更新草稿成果、提出更新建议。模型没有“确认进展”工具，确认由用户的 HTTP/UI 操作完成。

Work 输入分析只解释本次真实用户消息和明确选择的对象，不从附件、检索结果或引用文本推导写入授权。结果区分普通讨论、歧义、明确创建交付物、明确修改已有成果。明确指令生成持久化的 action 记录，绑定用户消息、操作种类、目标和基准版本；不确定时澄清，不使用宽泛关键词开放所有写工具。聚焦某成果本身只确定讨论对象，不等于授权修改。

AI 主动建议修改时保存 typed proposal，用户选择应用后由领域服务执行；保存建议不改变目标正文。进展建议用条目级 add/update/remove 表达，显示变更前后及依据；用户可编辑拟确认变更，确认请求校验结构和基准 revision。

成果保存使用经 schema 校验的结构化正文生成新版本。手动编辑由编辑器提交文档 JSON；AI 读取有稳定块身份的正文及文本投影，返回受限的块修改或明确请求的全文重写，再由领域服务生成同一种正文结构。未指定修改的标题、列表和表格应保留；文本转换只能处理已支持的格式，未知结构不能静默丢弃。具体块操作契约在阶段 1 固定，不引入任意 JSON patch 或任意 SQL。进展仍采用稳定条目 ID 的操作集合，所有正文变更都执行版本比较。

所有保存通过比较期望 revision 与当前 revision 执行。事务原子提交不可变版本、当前版本指针和操作结果。冲突返回当前版本和拟提交变更，前端保留编辑输入，不自动重新生成或覆盖。

确认同一个 proposal 多次返回原应用结果；确认时版本已变则返回冲突，proposal 保持可处理。忽略后没有新依据不重复提出同一建议，可按规范化变更与来源消息去重。同一次明确动作重复工具调用只能产生一个业务结果；操作键使用持久化的 turn/action ID，重复但输入不同则拒绝。

`capability.Context` 目前没有 tool_call_id，应补充这一事实以关联操作。业务事务和 runtime tool settlement 分属不同调用，不能假设天然原子：写入成功而 settlement/最终回答失败时，以 `t_work_operation` 查到真实结果；刷新后仍可展示“成果已保存，本次回复中断”。恢复核对操作结果，禁止无条件重新执行或自动撤销用户已保存的成果。

撤回新增恢复版本。默认针对最新修改；存在后续修改时返回差异供处理，避免丢失后续内容。手动编辑和 AI 修改共用同一版本服务，不维护两个正文来源。

### 6.1 共同编辑文档的第一版接入

用户已明确增加“人和 AI 都写同一份文档”，并确认按轮次修改，第一版采用轮流编辑。人手动保存后，将当前 artifact_id/revision 交给 AI；有未保存输入时先“保存并交给 AI”，保存失败则不继续修改。AI 工作期间显示同文档正在修改，完整正文保存后交还给用户继续编辑。新对话中的 AI 读取同一文档的最新已保存版本。轮次由明确编辑指令及完成/中断结果表达，版本按实际保存生成，两者不要求一一对应。

该功能复用本章成果版本与 action/operation 服务，保持唯一当前正文，不增加实时协同引擎。跨设备或迟到结果仍由服务器版本比较保护，不能仅依靠前端禁用编辑。详细方案和验收见 [共同编辑文档](2026-10-01-work-document-collaboration-design.md)。

## 7. 资料：复用文档链路并增加范围

关联现有共享知识库只保存关联，不复制内容；每次读取与工具调用核对当前可访问范围。Work 的空选择意味着无关联知识库，不继承普通聊天的全局默认。

建议为每个有上传资料的主题按需创建一个内部私有 KB，所有权记录在私有容器关联中，文件/链接复用现有 KnowledgeDocumentService、对象存储和 DocumentProcessService chunk 队列。对话附件和主题资料由 source 关联范围区分，同一主题内部也必须按可见文档限制检索。将附件加入主题只改变关联范围，不重复解析或修改来源正文。

私有 KB 必须从普通聊天、定时任务、知识库发现及全局列表的默认访问中排除，直接按 ID 的读取同样校验。不能仅靠名称前缀隐藏。既有共享库维持当前访问语义，不将 created_by 擅自解释成全仓库的成员权限。

检索范围建议表达为“KB → 允许的文档集合”：已明确关联的共享库可检索该库；内部 KB 仅检索当前主题资料、当前对话附件和明确选中资料。文档限制在查询层执行，涵盖向量、关键词、metadata、parent 回溯、预测问题原文和来源详情。受限请求在某通道不支持过滤时关闭该通道或报错，不能退回无范围检索。范围在 rerank 前生效，避免无关正文先进入外部 rerank。

第一版 Work 检索不启用未具备同等范围约束的全局 fact memory 或 wiki 补充通道。旧接口增加可选受限检索契约，普通请求行为保留；新增私有库排除是所有正式入口必须覆盖的条件。

用户上传文件/登记链接时创建 source，复用现有解析状态、重试和错误。URL 使用现有下载/抓取策略，补核对来源限制与重定向；文件大小、类型、处理预算与取消规则沿用或明确配置。未处理成功时不可声称已读。

已有 chunk 来源详情读取依赖管理员接口的部分，Work 新增用户范围内的资料、chunk 与原始内容读取入口。下载校验所属关系再提供内容或短期授权链接，不能通过公开对象 URL 绕过权限。此处必须核对实际对象存储访问配置，不能仅看 HTTP handler 判断私密性。

## 8. 前端与 API

路由建议 `/work`、`/work/:topicId`、`/work/:topicId/chat/:conversationId`。主题页包含可收起的对话列表、聊天和右侧进展/成果/资料面板。事项可选择“未分事项”或已有事项，允许手动新建；接续对话继承原事项，用户可调整。

消息展示与输入框从全局 store 耦合中提取必要的参数接入口，普通聊天保留原默认 adapter；Work 使用独立 store/controller，复用 SSE 消费和展示逻辑。状态键至少包括 topic/conversation/turn；切换后旧请求与流不能更新新主题的内容。手动编辑草稿按成果及基准版本保留，切换视图不丢失输入。

API 统一受登录保护，建议资源：topics、items、conversations/messages、artifacts/versions/restore、state/revisions、proposals/apply/ignore、sources/upload/promote，以及 chat/continue/stop。确认、恢复与资料提升要求显式请求；不在 GET 上产生写入。

聊天继续读取和停止必须核对 user/topic/turn 归属，即使 StreamManager 中已有缓存也不能仅凭 task ID 操作。Work 结构化事件通过现有 SSE 协议投影：成果已保存、建议已创建、引用等均以持久化对象 ID 为事实。刷新可通过消息/turn 的结果读取恢复卡片，不能只依赖短暂 stream cache。

列表采用有边界的分页，不照搬定时任务历史最多 100 条作为 Work 全历史语义。版本冲突使用现有错误响应约定增加可识别 code/currentRevision，前端显示差异并保留输入；实施前核对框架状态码映射。

## 9. 已确认的生命周期与清理实现

用户已确认主题归档/恢复、第一版不提供永久删除主题，以及删除对话时的保留边界：

- 主题可归档并恢复，归档后只读，保留资料、成果和进展；在途写入提交前复查状态。
- 第一版不提供主题永久删除；如需加入，先明确资料及历史保留规则。
- 删除对话保留独立成果和已确认进展，来源定位显示对话已删除；对话消息不继续通过隐藏索引被检索。未加入主题的对话附件随对话清理，已加入主题的资料不随原对话删除。
- 移除关联知识库或主题资料不删除既有共享库源文件；未来读取立即排除已移除范围。成果中已有的用户保存内容与可重新读取源资料分开处理。

Work 删除若复用现有会话删除事务，保留既有 scheduled-task 暂停/未读语义，并补 Work 关联、在途写入、历史索引与引用失效处理；不能直接绕开现有事务。

删除对话的事务先将该对话及待清理附件从可访问范围排除，并保存附件清理状态。后续复用文档删除服务清理 chunk、向量、原始文件和相关索引；失败可重试，HTTP/检索/下载不能因物理清理尚未结束继续访问附件。加入主题与删除对话并发时，按同一关联状态进行事务校验，已提升为主题资料的内容不误删。这里只清理该对话拥有的私有附件，不删除关联共享库的文件。

## 10. 实施与验收边界

实施前需核对普通聊天/SSE、KB 空范围、普通会话列表/删除、定时任务、全局画像观察和知识库读取的回归点。每阶段以真实受保护入口和 UI 验收，不以服务单测代替装配验证。

设计未提供独立调度或未经确认的后台 Work 执行。资料复用与权限过滤必须一起完成，未完成全局排除及查询限制前，不将用户私有材料写入沿用全局共享策略的容器。

编辑体验与生命周期产品边界已确认。编辑器选型、受限正文变更契约和清理恢复机制在实施中细化；数据模型、接口及验收计划按已确认产品范围推进。
