# 联调阻塞修复设计

## 背景

浏览器前后端联调发现三类问题：

1. `kb_demo_01` 绑定历史模型 `text-embedding-3-large`，当前运行配置只提供 `qwen-emb-8b` 和 `qwen-emb-local`，导致文档在向量化阶段失败。
2. 9090 端口运行的后端构建版本落后于当前仓库 HEAD，聊天流请求可能仍受旧 handler 实现影响，Wiki 请求长时间停留在“思考中”。
3. 远程 URL 上传请求不提交文件名，但后端在 URL 分支前统一要求 `fileName`，返回 `file name is required`。

## 目标

- 让联调知识库使用当前已配置且可用的 embedding 模型。
- 让远程 URL 上传依赖 URL/响应头推导文件名，不再被本地文件校验拦截。
- 让运行中的后端与当前 HEAD 一致，并重新验证聊天流和 Wiki 写入链路。
- 为模型解析和远程 URL 校验补充回归测试。

## 方案

### Embedding 模型对齐

只更新联调数据 `kb_demo_01` 的 `embedding_model` 为 `qwen-emb-8b`，不批量改写其他历史知识库，避免已有向量因模型或维度变化而失效。代码保留按知识库模型选择候选模型的行为，并补充模型 ID 不存在时的明确错误测试。

### 远程 URL 上传

将 `fileName`、文件体和文件大小校验限定到本地文件来源。URL 来源继续要求 `sourceLocation`，文件名交由远程抓取逻辑根据响应头或 URL 路径推导。保留本地文件上传的原有校验，并分别覆盖 URL 成功、本地文件缺少文件名和 URL 缺少地址的测试。

### 后端运行版本

使用当前 HEAD 构建新的 `goagent-server.exe`，停止监听 9090 的旧进程并启动新进程。启动后先检查进程构建版本和健康接口，再做浏览器联调，避免用旧二进制验证新代码。

## 验证

1. 定向运行模型路由、知识文档服务和 HTTP handler 测试。
2. 构建后端并确认构建版本为当前 HEAD。
3. 在浏览器中重新分块已上传 Markdown 文档，确认状态为 `success` 且分块数大于 0。
4. 发起 Wiki 生成请求，确认流式请求结束并在 Wiki 页面出现写入结果。
5. 使用远程 Markdown URL 上传，确认不再返回 `file name is required`。

## 非目标

- 不迁移 `kb-diag-1` 或其他历史知识库的 embedding 模型。
- 不在本次修复中重构 Wiki 生成逻辑或改变向量模型 API 协议。
- 不清理工作区中已有的 Vite 缓存改动。
